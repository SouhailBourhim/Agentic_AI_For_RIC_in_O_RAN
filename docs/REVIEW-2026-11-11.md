# Project review, 2026-11-11

A review of the whole repository at commit `000e320` (M09h frozen, not trained), against the
objectives of the proposal (`docs/Proposition_IA_agentique_RIC_ORAN_v2.pdf`). It answers one
question: **what stands between the project as it is and a project that reaches its objectives?**

How it was done: the proposal, `PLAN.md`, `DECISIONS.md` and the README were read in full; the
core path was read in code (`verifier/`, `agent/apply.py`, `agent/service.py`, `agent/graph.py`,
`store/a1_policy.py`, `rl/runner.py`, `rl/policy.py`, `gateway/server.py`, `backends/`); the
evaluation, plots, testbed scripts and C xApps were not read line by line. `ruff check` passes.
The test suite passes (526 tests, §6).

Nothing in the code was changed by this review. Every item in §4 is a proposal that needs its own
plan and approval, as `CLAUDE.md` asks.

## 1. Verdict in five lines

1. **The engineering objective is reached.** The full chain of the proposal's figure 2 exists,
   runs on the simulator and on a real OAI cell behind one interface, and the six hard invariants
   are enforced by tests.
2. **The scientific objective is not reached yet.** The proposal sets out to show that
   "LLM sets the objective, RL executes" does better than simpler designs. Today it beats static,
   RL only and LLM only where adaptation is needed, but **a hand-written formula behind the same
   agent and verifier matches or beats the RL policy** (M09b: 0.929 against 0.791 mean intent met
   on dev). That is the result a jury or a reader will ask about first.
3. **The cause is probably the environment, not the training recipe.** In the simulator the
   capacity is linear in PRBs and the offered load is given to the controller, so the best split
   has a closed form. RL has nothing to learn that arithmetic doesn't already know (§3.1).
4. **Three of the proposal's metrics are still missing:** the pre-registered comparison on test
   seeds (M09d), dangerous in-scope intents (M09f), and local against remote LLM cost and latency
   (M09i).
5. **The repository is hard to enter from outside:** no licence, no one-command demo, no short
   video, a README written for someone who already knows the project (fixed today, §5).

## 3. Findings, most important first

### 3.1 The simulator is too easy for RL to matter

This is the finding that decides whether the project reaches its main objective.

- In `sim/cell.py` every PRB carries the same rate, so a slice's capacity is `share × C`. The
  verifier already uses the inverse of this (`verifier/verify.py`, `required_shares`): a target of
  T Mb/s within a bound B needs `T / (C (1 − base/B))` of the cell.
- The controller is told the offered load of each slice (`rl/runner.py`, `seen_loads`).
- With a linear cell and a known load, the split that meets the targets is arithmetic. The
  formula controller does that arithmetic; the oracle confirms it is near the ceiling
  (0.97 / 1.00 / 0.92 / 0.84 / 1.00 against the oracle's 1.00 / 1.00 / 0.98 / 0.95 / 1.00).

So M09c and M09h are tuning a learner on a problem where the optimum is already written down.
v9 may close part of the gap, and its pre-registration should run as planned, but **even a v9
that equals the formula would not show why RL is needed.**

RL earns its place when the mapping from PRBs to service is unknown or changes:

| What a real cell has | What it does to the formula | Cost to add to the simulator |
|---|---|---|
| Per-UE channel quality (CQI/MCS) that varies in time, so Mb/s per PRB differs by slice and by second | The formula's `T / C` is wrong; it must be re-estimated online | Medium: a per-slice spectral-efficiency process in `sim/cell.py` |
| Offered load not observable, only throughput, buffer and delay | The formula can't size a slice it can't see the demand of | Small: hide `offered_load_mbps`; the runner already falls back to throughput |
| Several UEs per slice with different channels | Same as the first row, plus fairness inside a slice | Medium |
| Bursty traffic with heavy tails | Peak sizing wastes PRBs; a learner can trade risk | Small: a new traffic family in `sim/traffic.py` |

Proposed as **M10** (§4, P1): one harder simulator profile, the same benchmark, the same seven
controllers, with the formula given the same information as the policy. Either RL wins there, and
the claim is "RL is needed once the cell stops being linear and observable"; or it doesn't, and
the honest claim becomes "the value is in the intent → verifier → executor architecture, and the
executor can be a formula". Both are defensible. The current state is neither.

### 3.2 On the testbed, the controller reads the traffic generator

`backends/flexric.py` fills `offered_load_mbps` from the `traffic_target` table, which the iperf3
script writes (`store/testbed.py`). KPM does not report offered load. The M07b note says so
("the offered rate is an oracle") and measured that without it the policy freezes after the surge.

The README's limits do not mention it, and every testbed result depends on it. Two things to do:

- say it wherever testbed results are shown (done in the new README);
- replace the oracle with something a gNB can measure: RLC buffer occupancy or the PDCP volume
  KPM already exposes, turned into a demand estimate. This is the same work as row 2 of the table
  above, so M10 covers both.

### 3.3 The real-time loop has no safe state

Read in `rl/runner.py` and `backends/flexric.py`:

- **Stale KPM reports** are logged (`kpm_stale`) but the policy keeps deciding on the last values.
  A policy acting on frozen measurements can hold a bad split forever.
- **If the slice-control xApp dies**, `apply_prb_split` returns silently on every tick. The gNB
  keeps its last split; nothing restarts the xApp and nothing tells the operator beyond one event.
- **An exception in the policy or the backend ends the runner.** The gNB then keeps the last
  split with no controller.
- NaN or negative outputs are handled (`sim/cell.py:115`), and a lost database keeps the last
  objective until its expiry. Those two cases are good.

A real xApp has a fallback: after N ticks without fresh KPIs or without an acknowledged command,
apply a known safe split (equal, or the static one), raise an alert, and say so in `get_status`.
It is a small, deterministic change with clear tests, and it fits the project's safety story.

### 3.4 What the verifier guarantees, and what it doesn't

The verifier is the strongest part of the code: pure, ordered, tested, with reasons in numbers.
Its limit should be stated as clearly as its strength. It checks that an *objective* is feasible
and in the training range. It does not check that the *policy meets it*: M08d's S3 (0.53 against
static's 0.98) and M09b's F4a (0.27 against 1.00) are accepted objectives the policy then misses.

The agent's `observe → reflect` step sees this after the fact. What is missing is a runtime
monitor on the fast path: if a stated target is missed for N seconds while the formula's split
would meet it, switch the executor to the formula for that intent and log it. This is the
"exécutant à règles simples sous le LLM" fallback of the proposal's §9, made automatic. With it,
LLM + RL could never do worse than LLM + formula by more than the detection delay.

### 3.5 The evaluation is careful but narrow

- **Statistics.** M08 uses the median of 3 repeats; M09b is on dev seeds. M09d (paired
  differences with bootstrap intervals on untouched test seeds) is the fix and is already planned.
  Until it runs, no number in the repository is a claim.
- **Intents.** 40 annotated intents by one author, 20 held out, scored once: 19/20 has a 95 %
  interval of roughly 75–100 %. A second annotator on the same texts, or 60 more intents written
  by someone else, would make the extraction result much harder to dismiss.
- **`LLM only` cannot be simulated** (M09a), so its comparison rests on the testbed alone (M09e).
- **Latency is RLC delay**, not end to end. Fine, but the README's "< 10 ms" should say so.

### 3.6 Reproducibility from a clean clone

| Missing | Why it matters |
|---|---|
| A `LICENSE` file | Without one nobody may legally reuse the code; reviewers notice |
| Trained weights (the champion `.zip`, a few hundred kB) | `rl.plot_runner` and the live demo need a champion; a clean clone has none, and training takes hours |
| One command for the simulated demo | Today: five processes started by hand from the M04b note |
| A 60–90 s screen recording or GIF | The fastest way for anyone to see that it works |
| A testbed image registry or build cache | The patched gNB must be rebuilt from source |

Weights are excluded by `CLAUDE.md` ("do not commit model weights"). A GitHub Release asset
keeps the rule and solves the problem: `uv run python -m mlops.registry fetch-champion`
downloads and checks a hash.

### 3.7 Smaller things

- `pyproject.toml` says "RL xApp (DDPG)"; the champion is TD3. The README says TD3. `CLAUDE.md`
  says DDPG throughout. One line in `DECISIONS.md` explains the switch; the descriptions should
  agree.
- The README said 491 tests; the suite now collects 526. A hard-coded count goes stale: the new
  README links to the CI badge instead.
- No type checker in CI. The code has type hints everywhere; `pyright` or `mypy` in "basic" mode
  would catch what ruff's bug rules can't, at little cost.
- The agent's HTTP service has no authentication. It is safe today because it listens on
  localhost and has no endpoint that applies anything; say so in a short threat model
  (`docs/THREAT_MODEL.md`: who can reach what, and what each could do at worst).
- `notebooks/` has M01 and M02 only; the benchmark notebook promised in PLAN §9 is not there.
- `docs/learn/` has no index. Twenty-one notes need a one-page map (proposed in P3).
- The proposal names a co-author and a supervisor; the README says "personal project". If the
  code is yours alone, a line saying where the design came from avoids any question. Your call.

## 4. Proposed roadmap

In order. Each line is a checkpoint that still starts with its own plan.

### P0: finish what is already frozen (about 1 week, mostly machine time)

| Step | What | Who runs the long part |
|---|---|---|
| M09h | Train the six v9 arms as pre-registered; choose; confirm on `m10_test` | Souhail |
| M09d | Test-seed result, scored once, with the champion of that day | Souhail |
| M09e | Testbed confirmation, one night | Souhail |
| M09f | ~30 dangerous in-scope intents, unsafe changes applied must be 0 | Claude |
| M09i | Local vs remote LLM: accuracy, latency, cost on the same intents | Claude, with an API key |

### P1: make the main claim decidable (about 2 weeks)

- **M10a, a harder cell.** Time-varying spectral efficiency per slice, offered load hidden,
  bursty traffic. New simulator profile; old profiles untouched so every earlier result replays.
- **M10b, fair baselines on it.** The formula gets an online estimate of Mb/s per PRB (an
  exponential average of throughput / PRBs used), not the true value. Pre-register the comparison.
- **M10c, train and compare.** Same benchmark code, same seven controllers.
- **M10d, demand estimation on the testbed** from RLC buffer or PDCP volume, replacing the
  `traffic_target` oracle; rerun S1.

### P2: close the safety story (about 1 week)

- **Runner safe state** (§3.3): stale KPIs, dead xApp, exception → safe split, alert, status.
- **Runtime monitor with formula fallback** (§3.4), deterministic, on the fast path, tested.
- **Threat model** in one page, with the test that covers each line.

### P3: make it presentable (2–3 days)

- `LICENSE` (MIT or Apache-2.0: your choice).
- Champion weights as a release asset, with a fetch command and a hash check.
- `make demo` (or `uv run python -m demo`): starts runner, service, worker and exporter on the
  simulator with the rule-based parser, submits one intent, auto-confirms, prints the before and
  after. No GPU, no Ollama, under a minute.
- A 60–90 s recording of the Grafana dashboard during an intent, as a GIF at the top of the README.
- `docs/learn/README.md`: index of the notes, in reading order, one line each.
- A final "claims and evidence" table: one row per claim, the experiment, the number with its
  interval, the note. Then the report and the defence slides come from that table.

### What I would not do

- More tuning of the policy on the current simulator beyond M09h. The formula sets the ceiling
  there, and each round costs a held-out set.
- Multi-cell, mobility, or real radio hardware. Each is a project; none is needed for the claim.
- A web UI. Grafana and the console already show everything.
